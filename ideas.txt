A estrutura do projeto **CargaLog** foi organizada com uma abordagem de **Clean Architecture** e incorporando conceitos de **Domain-Driven Design (DDD)**, permitindo um sistema escalável, modular e de fácil manutenção. Abaixo estão os detalhes completos de como cada parte do sistema foi estruturada:

---

## **Visão Geral do Projeto**

**Nome do Projeto**: **CargaLog**

**Objetivo**: Registro e análise de progressão de carga em exercícios de musculação. O sistema permite que os usuários registrem dados dos seus treinos, visualizem a evolução do desempenho ao longo do tempo e gerenciem seus históricos.

---

### **Clean Architecture no CargaLog**

A **Clean Architecture** organiza o sistema em camadas de maneira que a lógica de negócios (entidades) é desacoplada de implementações externas (como bancos de dados, frameworks, etc.). Isso facilita a manutenção, a escalabilidade e a testabilidade do sistema.

#### **Camadas da Arquitetura**:

1. **Camada de Entidades (Entities Layer)**:

   * Contém as regras de negócio fundamentais do sistema.
   * **Exemplo**: **Usuário**, **Treino**, **Análise de Progresso**.

2. **Camada de Casos de Uso (Use Cases Layer)**:

   * Contém a lógica de aplicação e os fluxos de trabalho que atendem aos requisitos do sistema.
   * **Exemplo**: **Registrar Treino**, **Gerar Relatório de Progresso**, **Autenticar Usuário**.

3. **Camada de Interface (Interface Adapters Layer)**:

   * Adaptadores responsáveis por transformar dados entre o formato que o sistema usa e o formato exigido pelas interfaces externas (API, banco de dados, etc.).
   * **Exemplo**: **Controllers de API**, **Repositórios de Dados**.

4. **Camada de Frameworks e Drivers (Frameworks and Drivers Layer)**:

   * Contém as tecnologias de implementação, como frameworks, bancos de dados e interfaces externas.
   * **Exemplo**: **NestJS**, **TypeORM**, **React Native**, **React**, **PostgreSQL**.

### **Principais Mudanças com Clean Architecture:**

1. **Separação de Responsabilidades**:

   * **Entidades**: Contêm a lógica de negócios. Exemplo: a entidade `Treino` contém propriedades como carga, repetições e data.
   * **Casos de Uso**: Representam as tarefas que o sistema realiza, como **Registrar Treino** e **Gerar Relatório de Progresso**.
   * **Adaptadores**: **Controllers** que lidam com requisições HTTP e chamam os casos de uso apropriados.
   * **Frameworks/Drivers**: Implementações externas, como o banco de dados (**TypeORM**), frameworks de API (**NestJS**), etc.

2. **Isolamento das Regras de Negócio**:

   * A lógica de negócios é centralizada nas **entidades** e **casos de uso**, sem depender de frameworks ou bancos de dados específicos.
   * Isso facilita mudanças nas tecnologias sem afetar a lógica de negócios.

3. **Comunicação entre Camadas**:

   * A camada de interface (API, UI) se comunica com a camada de casos de uso, que interage com as entidades e repositórios.
   * Exemplos de endpoints:

     * **POST /auth/login**: Chama o caso de uso `AutenticarUsuario`.
     * **POST /treino**: Chama o caso de uso `RegistrarTreino`.

---

### **Benefícios da Clean Architecture:**

* **Flexibilidade e Escalabilidade**: Mudanças na interface ou tecnologias de banco de dados não afetam a lógica de negócios.
* **Testabilidade**: Facilita os testes unitários, pois a lógica de negócio está desacoplada das implementações de frameworks.
* **Manutenção**: As mudanças em uma camada não afetam as outras, facilitando a manutenção e evolução do sistema.

### **Arquitetura Clean Architecture no CargaLog**

A arquitetura do **CargaLog** é baseada em **Clean Architecture**, onde cada parte do sistema é organizada em camadas com responsabilidades bem definidas. Aqui não utilizamos microserviços, mas seguimos os mesmos princípios de modularidade e separação de responsabilidades.

---

### **Camada de Entidades (Entities Layer)**

As entidades representam os principais modelos de dados e as regras de negócio do sistema.

* **Usuário**: Representa o modelo de dados do usuário.
* **Treino**: Contém as propriedades e comportamentos do treino (exercício, carga, repetições, data).
* **Análise**: Responsável pela lógica de cálculo de progresso e evolução de carga.

### **Camada de Casos de Uso (Use Cases Layer)**

Cada caso de uso representa uma tarefa ou fluxo de trabalho que o sistema realiza.

* **Registrar Treino**: Caso de uso que registra novos treinos no sistema.
* **Gerar Relatório de Progresso**: Gera relatórios de evolução de desempenho.
* **Autenticar Usuário**: Realiza o login e validação do usuário.

### **Camada de Interface (Interface Adapters Layer)**

Essa camada contém os adaptadores que fazem a interface entre o sistema e as fontes externas.

* **Controllers**: Adaptadores que lidam com as requisições HTTP e chamam os casos de uso.

  * **auth.controller.ts**: Responsável por autenticar o usuário.
  * **treino.controller.ts**: Responsável por gerenciar os treinos.
  * **analise.controller.ts**: Responsável por gerar e exibir relatórios de progresso.
* **Repositórios**: Responsáveis pela persistência dos dados utilizando o **TypeORM**.

  * **treino.repository.ts**: Repositório de treinos.
  * **usuario.repository.ts**: Repositório de usuários.
  * **analise.repository.ts**: Repositório de análises.

### **Arquitetura de Domínio (DDD) no CargaLog**

O **Domain-Driven Design (DDD)** será incorporado ao projeto para garantir que o modelo de domínio reflita a complexidade do problema real, com ênfase no uso da **Clean Architecture** para organizar as camadas. O DDD se integra perfeitamente com a Clean Architecture, promovendo o desacoplamento das regras de negócios da implementação técnica.

---

### **Camadas da Arquitetura com DDD e Clean Architecture**

1. **Domínio (Domain Layer)**:

   * Contém os **modelos de domínio** (entidades) e **lógica de negócios** que representam as operações do sistema.
   * **Exemplo**: **Usuário**, **Treino**, **Análise de Progresso**.
   * Aqui, as entidades são definidas com foco na lógica do domínio e não nas necessidades da interface de usuário ou persistência de dados.

2. **Camada de Casos de Uso (Use Cases Layer)**:

   * Organiza a lógica de aplicação, os fluxos de trabalho e os casos de uso que atendem aos requisitos do sistema.
   * **Exemplo**: **Registrar Treino**, **Gerar Relatório de Progresso**, **Autenticar Usuário**.
   * Esta camada define os **serviços de aplicação** que orquestram as interações entre o domínio e a infraestrutura.

3. **Camada de Interface (Interface Adapters Layer)**:

   * Adaptadores responsáveis por transformar dados entre o modelo de domínio e os formatos exigidos pelas interfaces externas (API, banco de dados, etc.).
   * **Exemplo**: **Controllers de API**, **Repositórios de Dados**.

4. **Camada de Frameworks e Drivers (Frameworks and Drivers Layer)**:

   * Contém as tecnologias de implementação, como frameworks, bancos de dados e interfaces externas.
   * **Exemplo**: **NestJS**, **TypeORM**, **React Native**, **React**, **PostgreSQL**.

### **Principais Mudanças com DDD**

1. **Modelos de Domínio**:

   * As **entidades de domínio** (como **Usuário**, **Treino**, **Análise**) são mais ricas em comportamento e regras de negócios. Elas são separadas da lógica de aplicação (casos de uso) e da persistência de dados.

2. **Agregados e Objetos de Valor**:

   * Em vez de apenas ter entidades simples, podemos introduzir **agregados** (um grupo de entidades que são tratadas como uma unidade) e **objetos de valor** (tipos imutáveis que representam aspectos do domínio, como **Carga**, **Repetição**).

3. **Repositórios no Domínio**:

   * Os **repositórios** agora são interfaces dentro da camada de **domínio**, e a implementação concreta é feita na camada de **infraestrutura** (por exemplo, com **TypeORM**).

4. **Serviços de Domínio**:

   * Em vez de a lógica do domínio ficar em **casos de uso** ou **controllers**, a **lógica de domínio complexa** (como análise de progresso ou cálculos) pode ser encapsulada em **serviços de domínio**.
