A estrutura do projeto **CargaLog** foi organizada com uma abordagem de **Clean Architecture** e incorporando conceitos de **Domain-Driven Design (DDD)**, permitindo um sistema escalável, modular e de fácil manutenção. A aplicação dos princípios **SOLID** foi aplicada ao longo de toda a arquitetura, com ênfase especial na área de **domínio**, onde a aplicação de DDD justifica a estruturação e definição de cada componente. Abaixo estão os detalhes completos de como cada parte do sistema foi estruturada:

---

## **Visão Geral do Projeto**

**Nome do Projeto**: **CargaLog**

**Objetivo**: Registro e análise de progressão de carga em exercícios de musculação. O sistema permite que os usuários registrem dados dos seus treinos, visualizem a evolução do desempenho ao longo do tempo e gerenciem seus históricos.

---

### **Clean Architecture no CargaLog**

A **Clean Architecture** organiza o sistema em camadas de maneira que a lógica de negócios (entidades) é desacoplada de implementações externas (como bancos de dados, frameworks, etc.). Isso facilita a manutenção, a escalabilidade e a testabilidade do sistema. Além disso, a aplicação dos **princípios SOLID** dentro da arquitetura ajuda a garantir que o código seja coeso, flexível e fácil de modificar, promovendo um código robusto e de fácil manutenção.

#### **Camadas da Arquitetura**:

1. **Camada de Entidades (Entities Layer)**:

   * Contém as regras de negócio fundamentais do sistema. Aqui, aplicamos os conceitos de **DDD** para modelar as **entidades** de acordo com a lógica de negócio real, e **SOLID** é aplicado através do princípio da **Responsabilidade Única (SRP)**.
   * **Exemplo**: **Usuário**, **Treino**, **Análise de Progresso**.
   * A lógica de negócios dentro das entidades é orientada pelo domínio, garantindo que cada entidade tenha responsabilidade bem definida, sem depender de detalhes de persistência ou de interface com o usuário.

2. **Camada de Casos de Uso (Use Cases Layer)**:

   * Contém a lógica de aplicação e os fluxos de trabalho que atendem aos requisitos do sistema. Esta camada organiza os **casos de uso** do sistema, que são os pontos de entrada para a interação com o modelo de domínio.
   * **Exemplo**: **Registrar Treino**, **Gerar Relatório de Progresso**, **Autenticar Usuário**.
   * No uso dos princípios **SOLID**, o **princípio de Inversão de Dependência (DIP)** é aplicado, onde as dependências externas (como repositórios e frameworks) são abstraídas para que a lógica de negócios permaneça desacoplada da implementação concreta.

3. **Camada de Interface (Interface Adapters Layer)**:

   * Adaptadores responsáveis por transformar dados entre o modelo de domínio e os formatos exigidos pelas interfaces externas (API, banco de dados, etc.).
   * **Exemplo**: **Controllers de API**, **Repositórios de Dados**.
   * Aqui, o princípio **Interface Segregation Principle (ISP)** do SOLID é aplicado, garantindo que as interfaces usadas pelos adaptadores sejam específicas e coesas, evitando métodos desnecessários ou sobrecarregados.

4. **Camada de Frameworks e Drivers (Frameworks and Drivers Layer)**:

   * Contém as tecnologias de implementação, como frameworks, bancos de dados e interfaces externas.
   * **Exemplo**: **NestJS**, **TypeORM**, **React Native**, **React**, **PostgreSQL**.
   * Esta camada é onde a implementação concreta do sistema se conecta às camadas externas, mas sem violar o princípio **Inversão de Dependência (DIP)**.

### **Principais Mudanças com Clean Architecture, DDD e SOLID**:

1. **Separação de Responsabilidades**:

   * **Entidades de Domínio**: A lógica de negócios é encapsulada nas entidades de domínio. Exemplo: a entidade `Treino` contém as propriedades como carga, repetições e data, e a lógica associada. Essas entidades são projetadas com base no **DDD** e aplicam o **princípio de Responsabilidade Única (SRP)**.
   * **Casos de Uso**: Representam tarefas específicas do sistema, como **Registrar Treino** e **Gerar Relatório de Progresso**. A camada de casos de uso aplica os princípios **SOLID** para manter cada caso de uso simples e com uma única responsabilidade.
   * **Adaptadores de Interface**: **Controllers** que lidam com requisições HTTP e interagem com os casos de uso. Eles são projetados de forma a manter as interfaces de comunicação claras e coesas, conforme o **ISP (Interface Segregation Principle)** do SOLID.

2. **Isolamento das Regras de Negócio**:

   * A lógica de negócios é isolada nas **entidades de domínio** e **casos de uso**, de forma que as mudanças nas tecnologias de persistência ou nas interfaces externas não impactam a lógica do domínio, o que segue o princípio de **Inversão de Dependência (DIP)** do **SOLID**.

3. **Comunicação entre Camadas**:

   * A comunicação entre as camadas é feita de forma desacoplada, garantindo que mudanças em uma camada não afetem diretamente as outras. Isso é alcançado com o uso do **DIP**, onde as camadas superiores dependem de abstrações e não das implementações concretas.

DDD/SOLID será usado aonde o domínio justificar.

### **Stack Tecnológica Organizada**

**Back-End**:

* **NestJS**: Framework para construção da API, com foco em escalabilidade e performance.
* **TypeORM**: ORM para interação com o banco de dados **PostgreSQL**.
* **PostgreSQL**: Banco de dados relacional.
* **JWT (JSON Web Tokens)**: Para autenticação e autorização.
* **Criptografia**: Uso de **bcrypt** ou **argon2** para criptografia de senhas.

**Front-End**:

* **React Native (CLI)**: Para o aplicativo móvel (iOS/Android).
* **React**: Para o dashboard web.
* **Redux**: Para gerenciamento de estado nos apps **React** e **React Native**.

**Infraestrutura**:

* **Docker**: Containerização dos serviços para facilitar o deploy e escalabilidade.
* **CI/CD**: Pipeline de integração e entrega contínua utilizando ferramentas como **GitHub Actions**, **Jenkins**, ou **GitLab CI**.

---

### **Conclusão**

Com a incorporação do **Domain-Driven Design (DDD)** e da **Clean Architecture**, e alinhando os princípios **SOLID**, o **CargaLog** garante que a lógica de negócios seja robusta, testável e facilmente escalável. A separação das camadas permite que a aplicação seja modular, facilitando futuras mudanças e a manutenção a longo prazo. O uso dos princípios **SOLID** dentro do domínio, principalmente o **DIP** e **SRP**, assegura que a arquitetura seja flexível e adaptável ao longo do tempo.
